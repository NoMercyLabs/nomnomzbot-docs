Pipelines live on **Pipelines** in the sidebar.
A pipeline is a saved list of steps that the bot runs in order, such as a chat message and then a currency grant.
It runs only when a command, chat trigger, timer or event response points to it, so you can build and test one before anyone in chat can start it.

## Before you start

A **Moderator** or a higher role can make and change pipelines, and only those roles can try one from the editor, in a dry run or a live run.
A role that may only look sees the steps without the run and save buttons, and the editor shows "Your role cannot change pipelines."

The editor tries a pipeline in two ways, chosen in **How to run** above the steps.
**Dry run**, the default, records what each step would do and sends nothing.
**Run live** does everything the steps do, as you.
A step that works through OBS, the music player, VTube Studio or Discord needs that connection set up before you run it live.

## Make a pipeline

This example posts a line in chat and then gives the viewer some currency.
Fill in only the field each step below names, and leave the other fields of each step at their defaults for now.
A step card that says "Not set up yet", for example "Not set up yet: Message is empty.", is missing a field you fill in under **Step details**, and the line goes away once you fill it.

1. Open **Pipelines** and choose **New pipeline**.
2. Type a name in **Name** and choose **Make pipeline**.
   The editor opens with "This pipeline has no steps yet."
3. Choose **Add a step at the end**.
   **Steps to add** opens, grouped by area, with **Find a step** at the top.
4. Choose **Send message** under **Chat**.
   The step joins the pipeline, and its settings open in **Step details**.
5. Write your line in **Message**.
   Words in braces fill in from the run, such as `{user}` for the person who started it; [Variables and templates](/reference/commands/variables-and-templates) lists them.
6. Add **Grant currency** under **Economy** the same way, and set **Amount**.
   It adds to the balance of the person who started the run: the viewer who typed the command in chat, or you when you run it live from the editor.
7. Choose **Save** above the steps.
   The page shows "Pipeline saved."

**Step details** opens by itself only for a step you just added.
For a step that is already in the pipeline, choose its card to open it, and choose the card again to close it.

To change the order, drag a step by its handle, or focus the handle and press `Alt` with an arrow key.
**Duplicate** and **Remove** are in **Step details**.

Each step has **Keep going if this step fails**.
It is off by default, so a failure stops the pipeline at that step.

The first group in **Steps to add**, **Checks and groups**, holds blocks that contain other steps: **If, otherwise**, **Switch on a value**, **Pick one at random**, **Repeat**, **Catch a failure** and **Run on its own**.
The exact name and fields of every step are listed on [SDK types and payloads](/reference/code/sdk-contracts#action-parameters).

## Check it with a dry run

A dry run uses the steps in the editor now, including changes you have not saved, and it does not save them.
It really runs only **Set variable**, **Stop**, **Pick from list** and **Check balance**.
Every other step is only recorded and still counts as **Done**, so **Done** on **Send message** means the line would have gone out, not that chat got it.

1. Leave **How to run** at **Dry run**.
   The run button beside it reads **Test run**.
2. Look at the **Inputs** card at the top of the steps card.
   If it lists inputs, **Test run** opens **Test run inputs** first: fill in the values and choose **Continue**, as [Give the run some values](#give-the-run-some-values) explains.
   This example has no inputs, so its run starts at once.
3. Choose **Test run**.
   Each step card now shows its result: **Done**, **Failed** or **Did not run**.
   The run count in the header of the steps card, beside **Enabled**, counts them, for example "Test run 1: 2 steps ran."
4. The run button now reads **Clear test run**; choose it to take the results off the step cards.

Checks read the channel's real data, so the results show the path a real start would take.
A change to the steps clears the results.

### Give the run some values

A real start fills in values such as the viewer's name.
To try the pipeline with your own values, choose **Input** beside **How to run** to open **Test run inputs**.
When the pipeline declares inputs, the run button opens this dialog first, in a dry run and in a live run.

The **Inputs** card is at the top of the steps card, above the first step.
It holds the values a caller supplies when it starts the pipeline, and steps read them in braces.
To declare one, choose **Add input** and fill in **Name**, **Type** and **Description**.
A new input is **Required**; switch **Required** off to give it a **Default value** instead.
Choose **Save** to keep the inputs with the pipeline.

The dialog has a field for each declared input, labeled with the input's name.
Under each field is the input's **Description**, or "Enter JSON for number, boolean, list, and object values." when it has none.
A text input takes plain words; a number, true or false, a list or an object is typed in JSON, such as `5`, `true` or `["a", "b"]`.
**Continue** stays off until every input marked **Required** has a value and each value fits its type.
An optional input you leave empty uses its **Default value** from the **Inputs** card.

Below the fields, **Add a name and value** adds any other value the steps read in braces.
A row with the name `game` and the value `Chess` fills in `{game}` as Chess.
Choose **Continue** to start the run.
**Input** then shows how many values are set, for example **Input (2)**.

## Run it live

A live run does everything the steps do.
It starts as you, so **Grant currency** adds to your own balance, and a ban or timeout step acts on a real viewer.
It uses the steps in the editor the same way a dry run does, unsaved changes included.

1. Open each step card in **Step details** and check its fields, such as **Message** and **Amount**, because the confirm dialog lists the steps but not these values.
2. Select **Run live** in **How to run**, and choose the run button beside it, which now reads **Run live** instead of **Test run**.
   **Run this pipeline live?** opens; when the pipeline declares inputs, **Test run inputs** opens before it, so fill it in and choose **Continue**.
3. Read the list.
   It groups the steps by what they affect, with a warning on **Moderation** and **Economy**.
   A step that acts on a viewer named by a value in braces says so, for example "Hits whoever `{user}` names when the pipeline starts."
4. Choose **Run now**, or choose **Cancel** to close the dialog without running anything.
   After **Run now**, a notice at the top of the steps card lists the steps that ran, for example "Ran for real: Send message, Grant currency."
   Each step card shows its result, as in a dry run.

The run button reads **Clear test run** after a live run too, and it takes the results off the step cards the same way.
Only one live run of a pipeline goes at a time.
The editor goes back to **Dry run** each time you open it.

## Connect it to a command

You connect a pipeline on the **Commands** page, not in the pipeline editor.
The same choice has a different name on two screens: **Reaction** set to **Pipeline** in the command editor, and **What it does** set to **Runs a pipeline** in the new-command dialog.

For a command you already have:

1. Open **Commands** in the sidebar and choose the command in the list.
   Its editor opens.
2. Under **Reaction**, choose **Pipeline**, then pick your pipeline in the **Pipeline** field.
3. Choose **Save changes**.

For a new command, choose **New command**, set **What it does** to **Runs a pipeline**, pick your pipeline in **Pipeline**, and choose **Create command**.
[Create a command](/reference/commands/create-a-command) covers the rest of the command.
Chat triggers, timers and event responses can use a pipeline too, and one pipeline can serve several of them.

To get back to the pipeline, choose **Open in the pipeline editor** beside the **Pipeline** field, or open **Pipelines** in the sidebar and choose it in the list.
In the editor, the start line, the line with a lightning icon just above the first step, now names the command, for example "Starts when someone types !hug".
Type the command in chat: the bot posts your line, and the run shows under **Runs** with no **Test run** or **Live run** label.

## Read what a run did

Choose **Runs** above the steps.
The panel lists each start, newest first, with its outcome, when it started and how long it took.
A dry run from the editor carries the label **Test run**, and a live run from the editor carries **Live run**, so you can tell both from a real start.
Open a run to see **What each step did**, with each step's time and **Done** or **Failed**.
A run that went wrong shows its error.

## Switch off or delete

The **Enabled** switch at the top of the steps saves at once.
While it is off, the list and the editor mark the pipeline **Off**, and nothing starts it.

**Delete pipeline** at the bottom asks first and names each command, trigger, timer or event response that would stop running anything.

## Troubleshooting

::Troubleshooting

**The pipeline does nothing in chat.**
Check the start line above the first step: "Nothing starts this pipeline yet." means no command, chat trigger, timer or event response uses it.
Then check that **Enabled** is on.
Then open **Runs**: a failed run shows its error, and **What each step did** shows the step that stopped it.

**A dry run says Done, but nothing happened.**
That is how a dry run works: it records the step instead of running it.
Use **Run live** to make it happen.

::

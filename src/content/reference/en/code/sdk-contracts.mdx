Use this reference when you know which call or event you need and want its exact types.
The [script guides](/reference/code/sdk-script-basics) explain grants, errors and practical use; [Widgets, actions and templates](/reference/code/sdk-widgets-actions-templates) explains widget setup and event handling.
Scripts run synchronously inside the bot and use `nnz`; widgets run in the browser and use `NomNomz`, whose remote calls return promises.

In the declarations below, `?` means a property or argument can be omitted, `null` is an explicit empty result, and `A | B` allows either type.
Time values whose names end in `Ms` use milliseconds; date-time values are strings.
Types describe accepted shapes, while the linked guides explain limits, permissions and failure handling.
An action field marked optional can still depend on context, such as the viewer who triggered the run.

For declarations generated by your installed bot, use the [SDK discovery endpoints](#declarations-from-your-bot).
They also provide trigger-specific variables and widget-specific settings; those vary with the selected trigger or widget.
Widget payload fields here follow the generated TypeScript snapshot shipped with the dashboard.
The separate source-validation command compares that complete snapshot, including nested DTO fields, with freshly built C# reflection output; the standalone documentation build does not run that comparison.
Serialization tests also check representative host results, but do not cover every runtime value or provider response.
Use the installed bot's declarations and catalog when checking a different build's wire schema.
Maintainers can find the comparison and regeneration steps in the [documentation repository README](https://github.com/NoMercyLabs/nomnomzbot-docs#validation).

## Script calls and result types

These interfaces describe the objects under `nnz.api`, the grant-free helper namespaces and their result values.
The namespace names show which calls belong together: for example, `NnzApiStorageNamespace` describes `nnz.api.storage`.
They do not install an event bus in the script sandbox.
Use [Script basics](/reference/code/sdk-script-basics#the-bot-name) for the primitive `bot` facade, arguments and pipeline variables.

## Widget calls and result types

`NomNomz` implements `NnzOverlaySdk`.
The callback event names map to the [payload types below](#widget-event-names).
Catch rejected remote-call promises; an action result with `success: false` is a resolved refusal or failure, rather than a rejected transport promise.
Both `on` and `onAny` receive metadata at runtime, but the current typed `onAny` tuple declares only the event name and payload.
Use an event-specific `on` handler when you need the declared `meta` argument, including replay and test flags.

## Action parameters

Both `nnz.api.actions.invoke` and `NomNomz.actions.invoke` use this parameter map.
`NnzActionParams[T]` is the parameter object in the row for action type `T`.
Pass the action type as the first argument and its parameter object as the second.
An action with no required fields permits the second argument to be omitted.
Scripts need the grant for the literal action type; widgets run through their channel owner's permissions.
[Run a pipeline action](/reference/code/sdk-widgets-actions-templates#run-a-pipeline-action) explains that distinction and how to read the result.
These are input declarations; a value returned at runtime is not automatically a declared variable in the pipeline editor.
The [speech coordination example](/reference/audio/text-to-speech#coordinate-speech-with-other-steps) explains the extra declaration needed for `scene.token` in a saved pipeline.

## Stream metric types

These types are shared by `nnz.api.stats.stream` and `NomNomz.data.streamStats`.

In particular, `hypeTrain` can be absent when no train ended, although `NnzStreamMetricMap` declares it without `?`; `channel` is also omitted if its lookup returns no row.
Check those fields before reading their nested values.

## Declarations from your bot

The bot generates declarations from its own action, event and metric registries.
Use its dashboard API authentication and the `sdk:read` permission to request them from the bot's backend URL:

| Request | Response |
| --- | --- |
| `GET /api/v1/sdk/types.d.ts?context=script` | Plain-text TypeScript declarations for scripts. |
| `GET /api/v1/sdk/types.d.ts?context=widget` | Plain-text TypeScript declarations for widgets. |
| `GET /api/v1/sdk/event-catalog?context=script` | A JSON response with the script-visible event catalog in `data`. |
| `GET /api/v1/sdk/event-catalog?context=widget` | A JSON response with the public event catalog in `data`. |

The `context` value is case-insensitive and defaults to `script` when absent or blank.
Another value returns HTTP 400.
Widgets see public catalog entries; scripts see public, moderator and broadcaster entries, with internal entries excluded.
The catalog's wire names describe bot events; they are separate from the [widget subscription names](#widget-event-names).
Each catalog item has `wireName`, `tier`, `payloadSchema` and `samplePayloadJson`, which is a JSON string or `null`.
A sample can be generated from the reflected shape when no translated fixture is available; it is not proof that a live provider emitted those values.

The types endpoint also accepts a narrower context:

| Query | Purpose |
| --- | --- |
| `context=script&trigger=command` | Restricts `bot.getVar` suggestions to the variables a command trigger supplies. An event-response key can replace `command`. |
| `context=script&script=<script-guid>` | Resolves the selected channel's script triggers and combines their known variable keys. |
| `context=widget&widget=<widget-id>` | Types the selected channel's widget settings from its schema. |

Pass one of `trigger`, `script` or `widget` at a time.
A trigger or script applies only to script context, and a widget only to widget context; incompatible combinations return HTTP 400.
An unknown trigger returns HTTP 400; an unavailable script or widget returns HTTP 404.
A script without known usable trigger metadata keeps the general script declarations, and a widget without a usable settings schema keeps the general widget declarations.
This affects editor suggestions rather than adding capabilities to the running script or widget.

## Reader, task and prerequisites

Reader: a streamer/moderator setting access and pacing, or diagnosing why viewers differ from moderator tests. Main question: “Who can use this command, and when can they use it again?” Success: choose and save appropriate role/shared/personal waits, then correctly predict ordinary-viewer behavior and explain moderator bypass.

Prerequisites: an existing channel command, selected channel, command-write access (Moderator default, configurable upward), and knowledge of the Commands editor. To observe chat behavior: working connected bot, correct trigger, enabled command and live stream/offline opt-in for ordinary viewers. An ordinary-viewer account is needed to test ordinary cooldowns. TTS setup is needed only to hear permission denial; it is not needed to configure access/waits. Direct-bound timers/rewards follow their invocation rules and are outside these chat-message gates.

## Required coverage, grouped by original headings

- **Opening/settings table:** permission determines eligibility; cooldown paces eligible callers; Commands editor location/create link; chat-message scope versus bound rewards/timers; Who can use it plus shared and per-person whole-second settings, each 0–86400 seconds.
- **Set who can use a command:** first editor field, Everyone default; exact ascending ladder Everyone → Twitch subscribers → VIPs → Artists → Moderators → Lead moderators → Editors → Only you; chosen level or higher passes; save procedure and unsaved/saved feedback.
- **Platform distinctions within that heading:** these are bot levels, not a native-platform role equivalence. Twitch: subscriber/founder, VIP, moderator, lead badge, broadcaster; lead choosing ordinary badge proves Moderator unless stored standing supplies higher access; Artist badge alone is insufficient; Twitch Editor comes through stored team membership. Kick: subscriber/VIP/moderator/broadcaster, no native incoming Artist/Lead moderator/Editor inference. YouTube: member→Subscriber, chat moderator→Moderator, owner→Broadcaster; ordinary subscription is not membership; no incoming VIP/Artist/Lead moderator/Editor inference; Studio Editor is separate. Stored bot standing/team membership and active role permits can raise command access, including bot Lead moderator/Editor assignments for Kick/YouTube; assigning bot access does not grant platform moderation.
- **When a viewer’s role is too low:** command does not run; default chat notice “You don’t have permission to use that command.”; bot voice also attempts TTS regardless of command Read it aloud; channel TTS/playback gates and approval still apply; dashboard cannot currently review approval queue; positive minimum bits rejects zero-bit denial speech. Speech attempt limited to once/30 s/viewer/channel across denied commands; incoming broadcaster/moderator (including Twitch lead) exempt, stored role alone not exempt; attempt consumes wait even if TTS unavailable/refused; chat notices are not throttled by this speech guard. All three platforms share this path; lookup treats stored channel identity as Twitch even for Kick/YouTube; audio failure can coexist with chat notice.
- **Choose how often it answers:** shared useful for public answers, personal for individual responses, can combine; new custom defaults 0, presets/built-ins may differ; Trigger and cooldowns procedure, whole seconds/0 off/save feedback; folded heading shows both values or “No cooldown”.
- **How the two cooldowns work:** shared waits affect ordinary viewers; personal waits only caller; both must clear; role check precedes cooldown; each gate-accepted use starts respective waits, including operator uses; rejected role/cooldown attempts restart neither. Preserve 10 s shared/60 s personal example and intervening accepted use can extend shared wait beyond original viewer’s personal expiry; example values are not defaults. Do not promise downstream action success just because gates accepted the use.
- **Testing as a moderator:** incoming platform broadcaster/moderator flags bypass both checks on Twitch/Kick/YouTube, lead badge included; stored Moderator/Lead moderator/Editor alone does not; operator tests differ from ordinary viewers and still start shared waits; built-ins may add safeguards such as moderator skip window.
- **When a command is still cooling down:** no command execution, default “That command is still on cooldown.” chat notice; in-memory active waits clear on restart; saved lengths persist and next allowed use starts new waits.
- **Reset to the preset:** only seeded commands; dialog lists differing role/waits and other fields; preset values need not be zero; reply, description, aliases and trigger configuration also reset; name/enabled state preserved.
- **Troubleshooting:** permission refusal→lower requirement or assign appropriate role; platform moderator spam→expected normal bypass with extra built-in guard caveat; early post-restart use→active waits cleared.
- **Related pages:** preserve Create a command and Permissions, plus contextual TTS/approval and Built-in commands references.

## Exact evaluation questions and expected answers — evaluator only

1. **Primary task:** “Everyone should be allowed to use `!schedule`; chat should wait 10 seconds between accepted uses and each viewer 60 seconds. Which settings do you save?” **Expected:** Who can use it Everyone; Trigger and cooldowns → Chat cooldown 10, Per-person cooldown 60, Save changes. [CommandEditor:307-320,370-433; CommandDtos:135-140.]
2. **Prerequisites:** “Can a bot-assigned Editor who is an ordinary platform viewer test moderator cooldown bypass? What account would reproduce a normal viewer’s waits?” **Expected:** stored Editor can supply access but does not bypass cooldowns; use a non-broadcaster/non-platform-moderator account with sufficient access for normal waits. Working enabled command/chat/live-or-opt-in conditions still apply. [ChatMessageHandler:421-484,1301-1354,1949-1950.]
3. **Success:** “A uses at t=0, B at t=50 with 10 s chat/60 s personal waits. Can A use at t=60, and did A’s refused attempt at t=5 restart anything?” **Expected:** A’s personal wait ends at 60 and B’s shared wait ends at 60, so A may pass both at 60 (assuming no other accepted use/gates). Refusal at 5 restarts neither. [CooldownManager:35-49,78-87; ChatMessageHandler:421-484.]
4. **Application case:** “A Twitch viewer’s only platform badge is Artist and the command requires Artists. They have no stored role/permit. What happens, and if Read it aloud is off can the refusal still speak?” **Expected:** badge alone does not confer Artist command access; deny command and send default permission notice; denial independently attempts Bot TTS despite Read it aloud off, subject to TTS readiness/approval/minimum bits and per-viewer 30 s attempt throttle. No guarantee of audible delivery. [ChatRole:44-64; ChatTranslators:278-286; ChatMessageHandler:940-1028; TtsDispatchService:304-439.]

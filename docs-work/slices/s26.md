## Flows

Flow 1: write and save a script (editor, saved through `PUT code-scripts/{id}/project`).
1. Turn on the Custom Code feature on the Features page. Without it every code-script call answers "Custom code is not enabled for this channel. Enable it on the Features page." (CodeScriptsController.cs:267-277). The dashboard page that does this is outside this slice.
2. Create the script with a name (1 to 100 characters, unique in the channel). It is created enabled, language "typescript" (CodeScriptService.cs:168-191).
3. Save the project (one or more files plus a manifest with an `entry`). The bot checks: entry file exists, paths are safe, dependencies are on the allowlist (check is in `ProjectValidation`, not in this slice; CodeScriptService.cs:480-488).
4. The bot bundles with esbuild into one JavaScript file: TypeScript types removed, relative imports inlined, source map inside (EsbuildScriptBundler.cs:77-96). Then Jint parses it without running it (JintScriptExecutor.cs:282-285).
5. A bundle with problems is rejected: nothing is saved on this path, and the user gets the list of problems with file, line and column (`data.errors`) (CodeScriptService.cs:499-504, 723-735). On a good bundle a new version is appended and published at once, and the script's live version switches to it (CodeScriptService.cs:424-431).
6. The save fills in the list of capabilities the script uses (see Traps for how). That list is shown on the version.

Flow 2: run the script from a pipeline.
1. In the pipeline editor add the step "Run script" and pick the script in the "Script ID" field (help: "The saved code script to run.").
2. When a chat command, timer, reward, event response, webhook or pipeline trigger reaches the step, the bot loads the script. It must not be deleted and must be enabled. If not: "Script not found." or "Script is disabled." (ScriptRunner.cs:44-52).
3. The tenant quota is checked (only matters on hosted tiers). The script's published version must be valid and compiled, otherwise "Script has no valid published version." (ScriptRunner.cs:56-77).
4. The bot builds the grant from the saved capability list. If any listed capability is unknown, critical, or its feature is off, the whole run is denied: `Capability not enabled: <key>.` or similar text, outcome "Denied" (ScriptCapabilityBroker.cs:104-128, ScriptRunner.cs:100-115).
5. A fresh engine runs the script once, top to bottom, in strict mode. Variables the script sets are merged back into the pipeline. Text sent with `bot.send` becomes the step output. `bot.stopPipeline()` stops the rest of the pipeline (RunCodeAction.cs:70-78).
6. The step succeeds only if the outcome is "Success". Otherwise the step fails with the script's error message, or "Script did not complete successfully." (RunCodeAction.cs:76-78).
7. The script row stores `LastRanAt` and `LastRuntimeError` (null after success) and the elapsed ms are added to the month's usage (ScriptRunner.cs:135-146). The script list shows both.

Flow 3: test a script before it goes live (dry run).
1. Open the test run for a script (`POST code-scripts/{id}/test-run`). The request can carry: `args`, `variables`, a viewer `role`, a `trigger` sample, and optionally the unsaved `project` files (ScriptTestRunService.cs:100-129, 195-206).
2. Without project files, the live version runs. With them, the files go through the same save checks but are never stored. No valid version and no files: "Script has no valid published version to test." (ScriptTestRunService.cs:214-218).
3. The real engine and the real grant run. Reads are real: users, balance, storage reads, now playing, `http.fetch`. Writes are only recorded and a harmless success value comes back: `chat.send`, `chat.reply`, `music.queue`, `storage.set`, `storage.delete`, `tts.speak`, `tts.speakSequence`, `tts.voice.set`, `widget.emit`, `reward.update`, `schedule.pipeline`, and every `actions.invoke:<type>` (CaptureScriptHostBridge.cs:37-53, 67-74).
4. Argument checks still run in a test, so a bad write (empty message, oversize storage value, unknown widget) fails exactly like live and shows in `last.error` (CaptureScriptHostBridge.cs:86-96).
5. The result has: success, error (with "(line N, column M)" appended), duration, host call count, captured effects, chat output, a log, the variables the script changed, console lines, a timeline and the error position (ScriptTestRunService.cs:164-190).
6. A test run leaves no trace: no quota check, no usage record, no change to `LastRanAt` or `LastRuntimeError`, no chat, no TTS, no store write (ScriptTestRunService.cs:30-37).
7. Role in a test: `role` accepts a role word or alias (for example `mod`). An unknown role is refused: "Unknown role '<role>'." (ScriptTestRunService.cs:100-105, 261-268). A bad trigger: "Unknown trigger '<id>'." (lines 107-116).

Flow 4: versions.
1. Every save adds a version. Old versions can be listed.
2. Publish another version to switch back. It must have status valid ("Version is not valid." otherwise) (CodeScriptService.cs:272-276).
3. Delete an old version from the history. The live version cannot be deleted: "Can't delete the version this script currently runs. Publish a different version first." (CodeScriptService.cs:355-359). Deleting a version is a soft delete (row kept).
4. Delete the whole script. If a command runs it directly, it is refused: "This script is used by the command(s): <names>. Point them at another script or delete them first." (CodeScriptService.cs:543-547). The blast radius count lists pipeline steps that use it (up to 5 names) and the number of saved versions (CodeScriptService.cs:759-809).
5. Disable a script without deleting it: a disabled script fails at run time with "Script is disabled." and shows as unavailable in the step picker (ScriptRunner.cs:51-52, ScriptOptionProvider.cs:75-76).

Flow 5: find which triggers a script gets (SDK trigger keys). The resolver walks script, then its `run_code` steps, then the pipelines, then the rows that start them: chat commands, chat triggers, event responses (by event type), timers, rewards, webhook endpoints, pipeline triggers of kind "command" or "event". It follows `run_pipeline` steps in inline mode back to their callers, but not detached ones. Only enabled rows of this channel count. These keys decide which variables the editor offers (CodeScriptTriggerResolver.cs:38-157, 164-194).

## Flows
These are the task sequences the services support. Button and field labels are not in this slice (see the note under the title). Where a step names a label, it was copied from `event-responses/i18n/en.json`.

1. Turn on a reaction to an event (event responses).
   1. Open the page "Event responses" (crumb "Build"). The list shows the event types by their names, for example "New follower" and "Incoming raid".
   2. Open one event type. A new channel finds the row disabled, set to chat message, and following the platform default (EventResponseDefaultsSeeder.cs:86-89).
   3. The 18 default-on types already speak a line in the channel's tone (PlatformEventResponseDefaultsSeeder.cs:91-97). The other 32 stay silent until switched on.
   4. Type your own chat text, or pick a pipeline. Save. The save is an upsert of that event type (IEventResponseService.cs:32-37).
   5. After save the row owns its text. If you save text that equals the shown Informative default, the bot treats it as "no text" and keeps your tone (EventResponseToneCatalog.cs:86-99).
   6. Reset puts the row back to disabled with no message or pipeline. If a pipeline, command or action is bound, the first reset call fails and names the binding; a second call with confirmation resets it (IEventResponseService.cs:39-51).
2. Replay an event from the activity feed.
   1. Pick a past event in the activity feed and choose replay (`dashboard:replay`).
   2. The bot sends the chat line the event response would send, queues TTS, and shows the overlay alert. A gift bomb replays the gifter line and then each named recipient.
   3. The result is five counts. A count of zero means that part did nothing (for example the response is disabled). No currency, counter or stat changes (IActivityReplayService.cs:17-22; ActivityReplayResult.cs:14-17).
3. Delete a command that other things use.
   1. Ask for delete on a command. The dashboard can first read the blast-radius list: how many rewards, timers, event responses, chat triggers, giveaways and catalog items run it (ICommandService.cs:50-59).
   2. If any is bound, delete and disable are refused with COMMAND_IN_USE and the full list (ICommandBindingGuard.cs:31-34).
   3. Unbind the rows listed, then delete again. The delete is recorded in the channel's audit trail with who did it (ICommandService.cs:38-42).
4. Run a bot chat poll.
   1. Open a poll: question up to 200 characters, 2 to 10 options, optional auto-close in seconds, announce in chat (default true).
   2. If announce is on, the bot posts the question, the numbered options and how to vote.
   3. Viewers type the option number. A viewer's last vote counts. An expired poll closes on its next touch instead of counting the vote (IChatPollService.cs:17-22,50-53).
   4. Close the poll. The bot posts the result in chat and the poll stays in history (IChatPollService.cs:43).
5. Run a giveaway.
   1. Create a draft: title, entry mode (keyword or active viewers), keyword, entry cost, winner count, prize mode, optional scheduled close.
   2. Open it. Only one giveaway can be open or closed-but-undrawn. A second open fails GIVEAWAY_ALREADY_ACTIVE (IGiveawayService.cs:54-55).
   3. Viewers enter by keyword or the `enter_giveaway` action. Eligibility and entry cost apply (IGiveawayService.cs:69-71).
   4. Close (no more entries, still drawable), then draw. The draw picks distinct winners with a secure random draw weighted by tickets. It never picks the broadcaster; it skips moderators only when "exclude moderators" is on (IGiveawayService.cs:88-91).
   5. Redraw replaces one winner and excludes all earlier winners (IGiveawayService.cs:98-99).
   6. For a code-pool prize the winner gets the code by whisper. If the whisper failed, the broadcaster can reveal the code once to relay by hand (IGiveawayCodePoolService.cs:65-67).
6. Start a live game.
   1. Choose a game from the catalog (Crash, Drop Game, Heist, Raffle) and start it. It fails with SESSION_ALREADY_ACTIVE while another round is not finished, and needs an enabled game config (ILiveGameEngine.cs:25-30).
   2. Viewers join by typing the game keyword (`!crash`, `!drop`, `!heist`, `!raffle`) during the lobby window.
   3. If the round has too few players (Heist and Raffle need 2) it does not play out normally; the check is at LiveGameEngine.cs:481 (not read further).
   4. Cancel refunds every entry fee that has not settled (ILiveGameEngine.cs:37-40; IGameService.cs:93-97).
   5. If the channel has not installed the game's overlay widget, the round still runs and only the overlay stays dark (ILiveGameOverlayResolver.cs:14-18).
7. Set up a custom data source (outside data into events).
   1. Create a source, or pick a preset to pre-fill kind, endpoint, auth hint and field map (ICustomDataSourcePreset.cs:28-36).
   2. For a poll source, add the endpoint host to the channel's outbound allowlist first; otherwise nothing is fetched (ICustomDataEgressFetcher.cs:34-38).
   3. Use "test fetch" to see the real JSON and the list of field paths, then pick the keys (ICustomDataSourceService.cs:83-90).
   4. Use "test" with a sample payload to fire the event and wire an event response or pipeline to `custom.{name}`.
   5. Delete shows a count of event responses and widgets that use it. The count is a minimum, because templates and code scripts may name the source and cannot be read (ICustomDataSourceService.cs:96-102).
8. Read how a stream went.
   1. Open stream stats or a recap. With no stream id you get the latest stream, live or ended.
   2. Ask for chosen metrics; an unknown metric key fails VALIDATION_FAILED and names the first bad key (IStreamStatsService.cs:20-24).
   3. Build a recap to keep it. Building again for the same stream replaces the old recap (IStreamRecapService.cs:20-24).
